# Secure deployment checklist and operator responsibilities

Use this with the [threat model](threat-model.md), [installation guide](../installation.md), [security verification matrix](verification-matrix.md) and [runtime acceptance record](../runtime-acceptance.md). A checked configuration is not a certification or proof of production readiness.

- Choose one trusted team, one cluster, explicit namespaces and one application process/replica. All authenticated members share reports. Individual tenants and arbitrary identity headers are unsupported.
- Generate a random 32+ character team token and provision it through an existing Secret/secret manager. No password database, default password, stateless session signing key or account signup is used. Provider keys stay on the server; never use URLs, Helm values, screenshots or Git for credentials.
- Review installer permissions separately from the runtime Role. Do not grant Secrets, ConfigMaps, nodes, workload writes, exec, attach, proxy, port-forward, impersonation or RBAC modification. Run restricted-credential negative tests in a disposable environment before deploying elsewhere.
- Keep the Service internal. Local access binds/forwards 127.0.0.1. Shared access requires operator-provisioned TLS ingress, a trusted certificate, secure cookies and appropriate edge rate limits. HSTS is emitted only for configured secure-cookie HTTPS requests; a TLS-terminating ingress should set HSTS according to its own verified TLS configuration. No arbitrary forwarded identity headers are trusted.
- Keep API and provider TLS verification enabled. Insecure Kubernetes configurations are rejected. Do not solve certificate failures with insecure flags. Review administrator-controlled proxy/custom-CA environment settings and outbound network policy; the sample policy's HTTPS egress is broad, not an exfiltration guarantee.
- Leave logs disabled unless their diagnostic value outweighs disclosure risk. Review selected evidence and exports for remaining secrets/PII. Log controls now bound timestamp lookback (default one hour), bytes, lines and socket duration. Redaction of known multiline/PEM/connection-string forms is regression-tested, but arbitrary encodings and unknown formats may remain.
- Provide private writable SQLite storage with reliable locking, volume capacity/reserves, backups and a retention/deletion policy. File permissions are not encryption: use encrypted host/PVC disks and protected/encrypted backups where required. Deletion cannot erase historical backups or provider-side records.
- Keep workload writes/manual corrections outside the application. A fresh follow-up can establish absence of a specific observed condition, never global application health. A mock-provider result never proves live diagnostic accuracy.
- Retain operational/security events appropriately. Timestamped events cover authentication failures, denied access, creation/cancellation, export/deletion, configuration rejection and budget exhaustion with request/investigation IDs. Raw prompts, provider bodies, tokens and evidence are excluded. Logs are ordinary process logs; forward them to an operator-controlled collector/store for stronger retention and access controls. No tamper-proof audit storage is implemented.
- For source deployments, verify the interpreter loads patched SQLite (3.54.1+ recommended); pip cannot patch the host SQLite. The tested container is patched separately. The previous bundled interpreter still loads 3.53.1 and is rejected. The separately installed and tested source profile loads 3.54.1; follow installation.md rather than assuming all host interpreters were patched.
- Review locked dependencies, immutable action/base-image pins, known vulnerabilities, third-party notices and release artifacts. Resolve high-impact findings instead of suppressing them. Release signing/provenance, external review and non-executed environments remain separate gates.
- Before public release, the owner must verify a private vulnerability-reporting route and conduct-reporting route, review brand rights, and explicitly authorise any GitHub push/settings changes/workflow dispatch/publication. None is performed by this checklist.
